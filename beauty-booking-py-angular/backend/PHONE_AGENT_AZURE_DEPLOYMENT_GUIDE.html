Deploying the Phone Agent on Azure

This guide explains how to deploy your phone-agent endpoints safely, whether they interrupt your current website, and how to test before and after release.

Stack in this repo: FastAPI + Angular static files Voice endpoints: /api/voice/* Current orchestrator is a stub (no live ACS answer flow yet)

Will Deploying the Phone Agent Stop My Current Website?

Deployment Pattern Impact on Current Website Recommendation
Same App Service, direct deploy to production slot Possible short interruption (typically app restart window) during deployment. Use this on B1 with low-traffic deploy window and rollback package ready.
Same App Service with deployment slots (staging -> swap) Not available on B1 Basic. Requires upgrade to Standard or higher.
Separate App Service for phone agent API No interruption to existing website because workloads are isolated. Good isolation, but usually higher monthly cost.
On your current B1 plan, deploy directly to production and expect a short restart window. The safest approach is to deploy during low traffic and keep the previous ZIP package for immediate rollback.

Recommended B1 Deployment Plan (No Staging Slot)

  1. Use your existing Linux App Service: Anova in resource group anova.
  2. Build frontend and copy output into backend frontend-dist.
  3. Package backend for ZIP deploy.
  4. Set startup command on production app:
    gunicorn -w 2 -k uvicorn.workers.UvicornWorker app.main:app --bind 0.0.0.0:$PORT
  5. Configure voice environment variables on production app:
    • VOICE_DEFAULT_LANGUAGE
    • VOICE_FALLBACK_LANGUAGE
    • VOICE_FALLBACK_TRANSFER_NUMBER
    • VOICE_RETENTION_MODE
    • VOICE_BOOKING_PROVIDER
  6. Deploy ZIP to production and run smoke tests immediately.

Exact Deployment Commands for Your Current B1 App

# Run from C:\Repos\BeautyBooking

# 1) Build frontend
Set-Location .\beauty-booking-py-angular\frontend
npm ci
npm run build

# 2) Ensure backend has built frontend in frontend-dist
Set-Location ..\backend
# If your build output is not already copied automatically, copy it here.

# 3) Create deployment package (keep previous package for rollback)
if (Test-Path .\deploy-current.zip) { Remove-Item .\deploy-current.zip -Force }
Compress-Archive -Path .\app, .\requirements.txt, .\frontend-dist -DestinationPath .\deploy-current.zip -Force

# 4) Configure startup command on production app (one-time or when changed)
az webapp config set `
  --resource-group anova `
  --name Anova `
  --startup-file "gunicorn -w 2 -k uvicorn.workers.UvicornWorker app.main:app --bind 0.0.0.0:$PORT"

# 5) Configure required voice settings
az webapp config appsettings set `
  --resource-group anova `
  --name Anova `
  --settings VOICE_DEFAULT_LANGUAGE=da-DK VOICE_FALLBACK_LANGUAGE=en-US VOICE_FALLBACK_TRANSFER_NUMBER=+4542735479 VOICE_RETENTION_MODE=transcript-only VOICE_BOOKING_PROVIDER=setmore

# 6) Deploy ZIP to production (B1 direct deploy)
az webapp deploy `
  --resource-group anova `
  --name Anova `
  --src-path .\deploy-current.zip `
  --type zip

# 7) Smoke tests
curl https://anova.azurewebsites.net/api/health
curl https://anova.azurewebsites.net/api/voice/services?language=en

# 8) Live logs if needed
az webapp log tail --resource-group anova --name Anova

Expected behavior on B1: app restarts during deploy; plan for a low-traffic window.

End-to-End Call Flow (Customer -> Booking or Cancellation)

This is the exact runtime flow to implement and validate for the phone agent on your current backend.

  1. Customer calls your business phone number.
  2. Azure Communication Services sends inbound call event to /api/voice/call/incoming.
  3. Orchestrator accepts call and starts dialog (current code returns accepted status and fallback transfer number).
  4. Agent asks for intent: booking, cancellation, or general question.
  5. ACS speech/DTMF events are posted to /api/voice/call/events for turn-by-turn handling.
  6. If booking intent:
    • Agent gets services from /api/voice/services.
    • Agent asks for date and checks slots via /api/voice/availability.
    • Agent confirms selected slot via /api/voice/bookings.
    • Agent reads confirmation text and booking id back to caller.
  7. If cancellation intent:
    • Agent collects proof: booking reference OR service + start time.
    • Agent verifies via /api/voice/cancellations/verify.
    • If verified, agent confirms action and calls /api/voice/cancellations/confirm.
    • Agent reads cancellation reference back to caller.
  8. If intent is outside supported topics, agent transfers to fallback number (VOICE_FALLBACK_TRANSFER_NUMBER) or provides a fallback response.
Important current-state note: booking and cancellation API contracts are implemented, but live speech orchestration is still minimal. To get real phone conversations, you still need ACS event routing plus dialog logic inside the orchestrator.

What This Phone Agent Can and Cannot Handle

Caller Request Type Can Handle Now What Happens Required Improvement (if not handled)
Book appointment Partly API supports list services, availability, and booking confirmation. Voice conversation flow must still be wired in orchestrator. Add turn logic in /api/voice/call/events to collect service/date/time from speech.
Cancel appointment Partly API supports verify and confirm cancellation. Caller still needs dialog orchestration to collect proof fields naturally. Add guided cancel dialog and re-prompt handling.
"Is this the right place?" No (today) Current orchestrator does not contain business identity Q and A. Best fallback is transfer to staff number. Add identity intent with answer template like "Yes, this is BeautyBooking salon".
"Are you open on specific date/time?" No (today) No dedicated business-hours endpoint in current voice module. Agent cannot reliably answer opening-hours questions yet. Add opening-hours data source and intent route in orchestrator.
General small talk or unrelated questions No (today) Should fallback or transfer, otherwise caller experience will be confusing. Add explicit out-of-scope response policy and transfer rule.

Example Outcomes for Common Calls

  • Caller says: "Hi, is this the right salon?" -> Recommended behavior: short identity confirmation, then ask "Would you like to book or cancel?"
  • Caller says: "Are you open on 14 July at 18:00?" -> Recommended behavior: if hours data exists answer directly; otherwise transfer to staff.
  • Caller says: "I want to cancel my booking" -> Agent asks for booking reference, or service + appointment time, then verifies and cancels.
  • Caller says: "I need ladies haircut next Tuesday" -> Agent proposes slots from availability API and confirms selected time.

How to Test the Phone Agent

1) Local automated tests

cd beauty-booking-py-angular/backend
py -m pytest tests/test_voice_routes.py -vv

Covers incoming call events, services, availability, bookings, and cancellation endpoints.

2) Local manual API smoke tests

# Health
curl http://localhost:8000/api/health

# Incoming call event
curl -X POST http://localhost:8000/api/voice/call/incoming \
  -H "Content-Type: application/json" \
  -d '{"call_id":"call-123","from":"+4511111111","to":"+4522222222"}'

# Call event callback
curl -X POST http://localhost:8000/api/voice/call/events \
  -H "Content-Type: application/json" \
  -d '{"call_id":"call-123","event_type":"recognize_completed"}'

# List services
curl "http://localhost:8000/api/voice/services?language=en"

3) Production verification on Azure (B1)

  • Check GET /api/health on production URL after deploy.
  • Run the same voice API calls against production URL.
  • Validate website pages still load (home/book/contact/gallery/services).
  • Tail logs for errors:
az webapp log tail --resource-group anova --name Anova

4) End-to-end phone call test (when ACS event wiring is enabled)

  • Point ACS incoming call event to /api/voice/call/incoming.
  • Confirm callback events hit /api/voice/call/events.
  • Verify fallback transfer number and booking provider values in response and logs.

Rollback Plan for B1 (No Slot)

  1. Before each deploy, keep the previous working ZIP (for example deploy-previous.zip).
  2. If errors appear, redeploy the previous ZIP immediately:
az webapp deploy --resource-group anova --name Anova --src-path .\deploy-previous.zip --type zip
  1. Confirm recovery with /api/health and key voice endpoints.

Quick Decision

On your current B1 plan, deploy directly to production. It can cause a short restart window, so deploy in low traffic and keep a rollback ZIP ready.
